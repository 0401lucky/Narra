# Narra 发布与更新约定

## 1. 渠道

- 正式渠道：`release`
- 开发渠道：`dev`
- 基线渠道：`baseline`

对应包名：

- `release` -> `com.narra.app`
- `dev` -> `com.narra.app.dev`
- `baseline` -> `com.narra.app.baseline`

---

## 2. 版本比较

客户端后续检查更新时：

- 只使用 `versionCode` 判断新旧
- `versionName` 只负责展示

当前规则：

```text
versionCode = major * 10000 + minor * 100 + patch
```

---

## 3. APK 文件名

统一输出格式：

```text
Narra-v{versionName}-{versionCode}-{channel}.apk
```

示例：

- `Narra-v1.0.0-10000-release.apk`
- `Narra-v1.0.0-dev-10000-dev.apk`
- `Narra-v1.0.0-baseline-10000-baseline.apk`
- 当前开发分发包示例：`Narra-v2.2.12-dev-20212-dev.apk`

当前 dev 版本为 `2.2.12-dev / 20212`，APK 继续由 Cloudflare R2 分发，更新清单通过 GitHub Pages 发布；具体构建、校验和下载信息以 `发布候选记录.md` 为准。

---

## 4. 服务端更新元数据

建议按渠道分别维护：

- `release.json`
- `dev.json`
- `baseline.json`

推荐字段：

```json
{
  "app_id": "com.narra.app",
  "channel": "release",
  "latest_version_name": "1.1.0",
  "latest_version_code": 10100,
  "minimum_supported_version_code": 10000,
  "apk_url": "https://example.com/narra/Narra-v1.1.0-10100-release.apk",
  "apk_sha256": "必填，填写 APK 的 SHA-256",
  "published_at": "2026-03-22T12:00:00+08:00",
  "release_notes": [
    "新增功能 A",
    "修复问题 B"
  ]
}
```

说明：

- 当前客户端统一按“可选更新”处理，不启用强制更新。
- `minimum_supported_version_code` 仅作为兼容保留字段，建议填写 `0` 或不高于当前已发布版本。
- 当 `latest_version_code` 高于本地版本时，`apk_url` 和 `apk_sha256` 都是必填字段；缺少校验值会被客户端拒绝。
- dev 包默认上传到 Cloudflare R2 的 `narra-updates/dev/` 目录，并通过 `https://download.lsa1230.dpdns.org/dev/...` 分发。
- 本机历史流程使用 `wrangler r2 object put ... --remote --content-type application/vnd.android.package-archive` 上传；新 Actions 流程使用 R2 的 S3 接口及仅限本桶的 Object Read & Write 凭据，上传时同样设置 APK MIME 类型。
- 若自定义下载域名曾缓存过 404，可在 `apk_url` 后追加版本查询参数，例如 `?v=20002`。

---

## 5. 发布前验证建议

每次更新 `dev.json` 前建议至少完成：

1. `.\gradlew.bat testDebugUnitTest --console=plain`
2. `.\gradlew.bat assembleDebug --console=plain`
3. `Get-FileHash` 校验 APK SHA-256，并写入 `apk_sha256`
4. 用 `wrangler r2 object get --remote` 拉回远端对象并再次校验 SHA-256
5. 用 `Invoke-WebRequest -Method Head` 确认公开 APK URL 返回 `200`
6. 确认失败重试与渠道隔离逻辑没有被本次改动破坏

---

## 6. GitHub Actions 自动 dev 发版

工作流入口为 `.github/workflows/dev-release.yml`，只接受本仓库 `main` 的手动触发。先把目标版本的构建配置、`CHANGELOG.md` 待发布条目及 `docs/updates/dev-release-notes.json` 提交到 `main`，再在 Actions 页面选择 **Run workflow**，或使用：

```powershell
gh workflow run dev-release.yml --repo 0401lucky/Narra --ref main -f version=2.3.0
```

输入不带 `-dev`，必须与源码中的 major / minor / patch 一致。触发后按顺序完成：

1. 锁定源码提交，恢复既有 dev 签名，运行单测、Lint、截图 verify 和 debug 构建。
2. 检查 APK 实际版本、包名、证书与 SHA-256，保存 APK 及无密钥的来源报告到 Actions artifact。
3. 将 APK 上传到 `narra-updates/dev/`，远端回拉校验，再验证公开链接的状态与下载内容。
4. 校验通过后才提交新 `dev.json`、版本状态及候选记录。
5. 显式调用 Pages 部署，并读取公开清单核对字段后报告完成。`GITHUB_TOKEN` 的普通 push 不会自动触发下一条 push 工作流，不能省略这一步。

普通 push / PR 继续执行原 Android Quality，既有手动截图 record 仅生成供审阅的候选基准，不作为发版通过条件。

### 仓库配置

| 名称 | 类型 | 用途 |
| --- | --- | --- |
| `NARRA_DEV_KEYSTORE_BASE64` | Actions Secret | 既有 dev keystore，保证覆盖升级证书一致 |
| `R2_ACCESS_KEY_ID` | Actions Secret | 仅 `narra-updates` 的 S3 对象读写凭据 |
| `R2_SECRET_ACCESS_KEY` | Actions Secret | 与上述 Access Key ID 配对 |
| `CLOUDFLARE_ACCOUNT_ID` | Actions Variable | 核对既有桶后构造 S3 endpoint |
| `R2_JURISDICTION` | 可选 Actions Variable | 默认 `default`，只有既有桶要求其他 jurisdiction 时才设置 |

R2 的 Object Read & Write 权限仅支持 S3 API，不能用它直接替代本机 Wrangler OAuth。凭据限制到既有桶，脚本进一步固定 `dev/` 前缀；不为发布扩大到管理桶、账户、DNS 或其他仓库。密钥只通过安全输入配置，不写进文件正文、命令输出或公开 artifact。

现有 dev 签名证书 SHA-256 为 `3a6c57eec0641bc00830252eb821d62c9e9b2f639c5989d0bc42b29b843546e8`，CI 必须核对还原的 keystore 和最终 APK，不能使用 runner 临时生成的新证书。

### 失败和重试

- 构建失败先修复并重新验证；发布阶段失败优先重跑失败 job，复用已成功构建的 artifact。
- 同版本 R2 对象存在且哈希一致时可以继续验证；哈希不同则停止，使用原 artifact 或另发更高版本。
- R2 的 403、认证失败及网络错误不能当作“对象不存在”；远端或公开下载校验失败时不提交新清单。
- Pages 发布失败或公开清单仍未更新时，发版尚未完成，可以重试部署；不删除历史 APK，也不自动降级线上版本。
- 客户端仍只信任现有 Pages 清单地址和 R2 自定义下载域名，不能直接用任意 `r2.dev` 地址替代。签名与包名一致的检查不等同于真机覆盖安装实测，设备验证须单独记录。
