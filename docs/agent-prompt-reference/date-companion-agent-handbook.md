## 1. 一句话理解这个功能

**把与同一角色的互动，从“隔着手机发消息”切换成“待在同一场景里相处”，并用可切换的立绘演出与连续阅读呈现同一段经历。**

核心闭环是：

```text
选角色
  -> 选择谁主动靠近，或者不生成开场
  -> 角色以面对面场景回应
  -> 用户说话 / 写动作 / 点「继续」留白
  -> 新的一轮场景与台词
  -> 原文及时保存
  -> 回到聊天后仍知道刚才发生过什么，但恢复聊天格式
```

它不是靠一个特别复杂的“陪伴算法”成立，而是几个机制配合：

1. **关系不断档**：沿用已有角色、用户身份、历史与可读记忆，不新建一个失忆副本。
2. **互动媒介改变**：允许环境、距离、动作、停顿和沉默，不只输出 IM 气泡。
3. **用户可以暂时不贡献新内容**：「继续」让角色主动回应，但不接管用户的决定。
4. **文本与演出分层**：模型生成正文，解析器把正文投影成立绘、台词、旁白、语音与观测。
5. **控制权仍在用户**：可以换文风、编辑、重生成、删除、回看和离开。

“真实见面”“面对面共处”是角色扮演的场景框定，不表示程序证明了物理共处，也不意味着模型真的看见了用户。

### 1.1 不要把这些同名概念合并

| 名称 | 当前含义 | 本文处理方式 |
| --- | --- | --- |
| 见面首页「陪伴」 | 单角色传统见面，`DateApp` + `DateSession` | 主体 |
| 见面首页「剧情」 | 独立剧情条目、多人、面具身份、原生预设、事件盒 | 只说明边界 |
| 剧情中的「真实时间陪伴」 | 剧情的一种记忆写入模式，给角色时间线写副本 | 不当成本文主实现 |
| 桌面陪伴 | 桌面模型/图片、触摸、语音等 | 可复用立绘资产，但控制器不同 |
| 3D 小屋陪伴 | 寻路、家具、居民、本地自主行为 | 不要求移植 |
| 专注/计时陪伴 | 番茄钟、任务计时、专注统计 | 本功能没有这条主流程 |

## 2. 产品能力地图

| 能力 | 用户可感知的行为 | 实现性质 |
| --- | --- | --- |
| 角色选择 | 分组筛选、横向分页，单页最多 6 位角色 | 本地 UI |
| 三种开场 | 靠近他 / 让他靠近 / 直接见面 | 前两种请求模型，第三种不请求 |
| 面对面回复 | 台词与动作分行，参考既有关系与场景 | 模型 + 场景提示词 |
| 主动留白 | 点击「继续」，用户无需输入新台词 | 每点一次发起一个新回合，不是定时自动运行 |
| 立绘模式 | 当前表情、逐句文本、打字机、手动推进和循环重播 | 本地播放引擎 |
| 阅读模式 | 连续查看当前角色的见面原文，加载更早记录 | 同一数据库的另一种视图 |
| 观测面板 | 时间、地点、状态、细节及自定义项 | 同次回复附带结构化文本，不单独请求模型 |
| 文风与人称 | 5 种文风、3 种显式叙事人称、自定义补充 | 改变之后的生成，不改旧消息 |
| 场景与服装 | 背景、表情立绘、皮肤套装、缩放和位置 | 本地显示配置，不等于模型看图 |
| 语音 | 台词播放、可选翻译、部分服务商的流播放与连续朗读 | 独立 TTS 能力，有额外费用 |
| 修订 | 普通发送失败重试、最新回复重生成、编辑/删除/多选 | 存储和请求控制 |
| 历史整理 | 按次/按日期、年月筛选、日期定位、TXT 导出 | 不受 AI 记忆水位隐藏 |
| 记忆衔接 | 共享角色原文；符合条件时后台整理长期记忆 | 复用公共记忆系统 |
| 跨 App 衔接 | 从聊天来、回聊天去，模式切换但经历保留 | 路由 + 上下文来源标记 |

当前没有独立的陪伴时长结算、结束奖励、好感加分、强制结束总结、自动换背景、每隔几分钟自动续写或离线生成保证。不要因为名称叫“陪伴”就自行补成这些功能。

## 3. 完整用户旅程

### 3.1 从桌面打开

1. 打开「见面」，默认落在「陪伴」。
2. 看角色头像卡；可按角色分组筛选，6 人一页横向翻页。
3. 点击头像卡才进入开场选择。卡片里的齿轮和记录按钮有独立点击路径，不应误触发见面。
4. 第一次到达开场选择页，会出现一次性三选项说明；本机标记已读后不重复展示。
5. 选择开场并进入会话。
6. 离开当前会话回选择页；从 App 顶层离开则回桌面。

角色卡上的“在线”是当前页面绘制的徽标，不能据此推断存在联网在线状态服务或角色正在后台运行。

### 3.2 从聊天打开

聊天加号操作中的见面入口调用 `openDateWithChar(charId)`：设置目标角色、投递一次性导航意图、打开 DateApp。

- 不需要用户再挑一次角色。
- 仍然要选择这次的开场方式，并非自动调模型。
- DateApp 记住 `cameFromChat`；退出开场或会话时回 ChatApp，而不是掉回桌面。
- 这个来源标记只活在本次 DateApp 挂载中，不能污染以后从桌面打开的会话。

另有快捷导航入口可直接进入指定角色的准备、设置、记录，或切到剧情；打开入口本身不应生成开场。

### 3.3 三种开场的精确定义

| 选项 | 生成任务 | 用户下一步 | 保存边界 |
| --- | --- | --- | --- |
| 靠近他 | 第三人称描述角色此刻在做什么、环境和状态；不新增用户到场动作或双方互动 | 看开场后点「走过去」 | 点击进入会话后保存选中的开场 |
| 让他靠近 | 结合已有地点、约定、关系和动机，让角色自然靠近/开口；不代写用户接受或反应 | 看开场后点「见到他」 | 同上 |
| 直接见面 | 不生成开场 | 直接输入，或点「继续」让角色先行动 | 第一条实际回合开始保存 |

前两种先进入“正在感知”的等待页，成功后可重新感知、进入场景布置，或悄悄离开。空回复和请求失败也保留重试/退出入口，不能出现只剩角色名的黑屏。

**开场预览不等于已经发生的共同经历**：源码先把它放在 `peekStatus`，只有点「走过去/见到他」并保存成功，才进入会话。预览期间重新生成的废稿、未接受就离开的开场不落消息库。

进入会话时先保存开场，再允许后续互动。否则第一次用户说话时，模型可能读不到自己刚生成的场景。

### 3.4 一段自行构造的体验示例

以下不是实测模型输出，也不是项目角色素材。

```text
已有经历：用户阿宁和角色林澈约好一起整理旧唱片。

阿宁选择「靠近他」
  -> 开场：林澈在桌前分拣唱片，窗边有尚未收起的包装纸。
阿宁点「走过去」
  -> 开场成为本场第一条 assistant 原文。
阿宁输入：「我只想坐一会儿，今天先不整理了。」
  -> 林澈放下手里的东西，接住这句话，而不是强迫继续任务。
阿宁点「继续」
  -> 记录里显示「（继续）」。
  -> 林澈可以继续自己的小动作、开一句话或共享沉默。
  -> 不能替阿宁写“点了点头，靠过去接受拥抱”。
阿宁切到阅读模式
  -> 看到同一份正文，不重新调用模型。
阿宁离开，回聊天说：「刚才那张唱片叫什么？」
  -> 聊天可参考刚才的见面经历，但回复恢复成聊天格式。
```

## 4. 最值得迁移的交互原则

### 4.1 主动，但不替用户作主

“继续”不是空请求，也不是把上一条答案继续输出几个 token。它是一个新的用户回合，含义是：

- 用户这一轮没有新增主动台词和动作。
- 双方仍处于当前面对面场景，不默认离场，也不切回线上。
- 角色根据自己的性格、意愿、既有因果与现场进行下一小步。
- 不机械反问“你接下来想做什么”。
- 用户未写出的接受、身体反应、内心、决定和关系升级不能被代写。

有一个必须在目标项目明确解决的张力：当前“继续”指令倾向要求有具体新变化，末尾人物原则又允许普通动作与共享沉默。建议把“变化”理解为场景自然运行，不设定每轮必须升级情绪或关系的硬指标。

### 4.2 文风不是人格控制器

当前提示词明确区分：

- **身份、经历、当前证据**决定角色怎样行动。
- **文风**决定怎样描写。
- 风格示例不能成为每个角色都模仿的性格模板。
- “浓烈”不等于必须制造冲突、接触或亲密升级。
- 用户表达不愿意、想停止、纠正理解或换话题，应真实改变角色下一步。
- 角色可以拒绝、不同意、迟疑或继续自己的事，不必被统一抹成温柔口吻。

这些是生成目标，不是模型行为的数学保证。目标项目应使用情境验收，而不只检查 prompt 中出现了某句话。

### 4.3 推进、继续和重生成不能混淆

| 操作 | 是否调文本模型 | 是否新增经历 |
| --- | --- | --- |
| 点场景推进下一句 | 否 | 否，只播放已有文本 |
| 一轮播完再次点场景 | 否 | 否，循环重播本轮 |
| 点「继续」 | 是 | 是，保存新的用户占位和角色回复 |
| 点「重新生成」 | 是 | 替换最新候选回复，不是追加新剧情 |
| 切阅读/立绘、展开 HUD | 否 | 否 |
| 播放声音 | 不一定调文本模型；非默认语种可能先翻译 | 不改原文，但可能发生 TTS 费用 |

不要让用户以为“Loop”会无限自动请求模型，也不要让普通点击推进承担隐蔽计费。

## 5. 页面结构与状态机

### 5.1 App 级状态

源码的页面模式是：`select / entry / peek / session / settings / history`，旁边另有 `companion / story` 表面选择。

```text
select --角色卡--> entry --靠近/被靠近--> peek --保存开场成功--> session
                     |                    |
                     +--直接见面----------+-----------------> session
                                          |
                                          +--重新感知--> peek

select --齿轮--> settings --返回--> select
peek   --布置--> settings --返回--> peek
select --记录--> history  --返回--> select
session --布置--> 内部设置覆盖层 --返回--> 原 session
session --离开--> select / 原聊天入口
```

会话内设置是覆盖层，不把父级改成 `settings`，因此临时离开画面布置场景不会重新挂载播放器、丢失当前播放队列。

### 5.2 会话内至少分成四组状态

| 状态组 | 当前字段示例 | 是否应视为权威数据 |
| --- | --- | --- |
| 消息与场次 | `historyMessages`、`encounterId` | 消息库权威；列表只是已加载窗口 |
| 播放器 | `dialogueBatch`、`dialogueQueue`、`currentText`、`displayedText`、`currentSpriteKey` | 可由原文重建 |
| 交互与请求 | `input`、`isTyping`、`pendingRetryText`、菜单、设置、多选 | UI 临时状态 |
| 声音 | 当前音频、生成代次、字幕时间轴、音频缓存 | 独立资源生命周期 |

**不要把“浏览了上一场的消息”解释为“恢复了上一场的运行状态”。** 阅读模式可以看所有见面记录，但当前立绘演出、重生成和失败重试只操作当前场次。

### 5.3 离开不再保存播放器快照

当前生产入口不再提供“继续上次”，不周期性写 `savedDateState`，也不恢复“上次播到第几句”。

- 正常选角色产生新的 `dateEncounterId`。
- 消息逐条落库，所以离开无需“保存并退出”的确认框。
- 普通选角色会清理角色上残留的旧恢复字段；快捷准备入口不主动丢弃旧字段，但同样不使用它恢复。
- `DateState`、`initialState` 兼容分支和恢复哨兵工具仍存在，不代表当前用户能触发恢复。

如果目标项目确实需要断点续播，应另做版本化的轻量书签，例如 `messageId + beatIndex + viewMode`，不能把整段历史、背景和立绘 base64 再复制进一个运行快照。

## 6. 数据模型与持久化契约

### 6.1 当前原文没有单独的 date_messages 表

使用公共 IndexedDB `messages`，与私聊、通话等共用角色时间线。见面消息的关键字段：

```ts
// 摘要化字段说明，不是建议直接复制本项目的全部类型。
type DateMessage = {
  id: number;                    // 数据库自增主键
  charId: string;                // 角色 ID
  role: 'user' | 'assistant';
  type: 'text';
  content: string;               // 持久原文，保留协议标记
  timestamp: number;             // 实际保存时刻，绝对时间戳
  metadata: {
    source: 'date';
    dateEncounterId: string;     // 当前场次
    isOpening?: boolean;
    dateOpeningMode?: 'approach' | 'invite';
    meetingContinue?: boolean;
    // 可选 SAR 等集成字段，不是基础功能的必需项。
  };
};
```

在当前通用 `Message` 中 `metadata` 是宽松类型；上面的结构由使用处形成约定，并非已经有严格 schema 校验。

`dateEncounterId` 当前存在于消息 metadata，不是独立持久化的场次实体。空场次退出后没有消息，自然也没有一条可回看的场次记录。

### 6.2 保存原文，而不是保存渲染结果

一条 assistant 消息可能包含整轮多行正文：

```text
⟦OBSERVE⟧
时间｜唱片店打烊前
地点｜靠窗的长桌
状态｜放松下来，手里还拿着唱片套
细节｜先把桌边的空椅子拉开了一点
⟦/OBSERVE⟧
[normal] 林澈把纸套放平，没有急着继续整理。
[happy] "那就先坐一会儿。" [v:calm]
```

- 整段以一条消息保存，不按视觉上每行再造数据库消息。
- OBSERVE、立绘标签、语音标签仍留在原文里。
- 展示、播音、导出分别选择合适的投影，不能用一个“去掉所有方括号”的函数处理一切。
- 单条长消息仍是一条消息；上下文的消息条数不等于 token 预算。

### 6.3 「继续」的显示文本与调度指令分离

数据库仅保存：

```text
content = （继续）
metadata.meetingContinue = true
```

本次生成时再把它转换成面对面留白的完整任务说明。这样不会把多段技术提示词当作用户原话显示、导出或反复写入长期记忆。

**建议改进**：目标项目把它定义为语义化 `turn.kind = 'continue'`，发送、失败重试、重生成都从同一个转换函数恢复含义，而不是散落地比较占位字符串。

### 6.4 保存成功的含义

`DB.saveMessage`、`DB.updateMessage` 等会等待 IndexedDB 事务提交，不能把 `request.onsuccess` 当作最终成功。配额不足、事务终止时，UI 不应宣称已经保存。

不过“调用两次各自可靠的 DB 方法”不等于跨方法原子操作：当前重生成的删旧/存新是两次事务，这一点在第 17 节单列。

### 6.5 角色级配置字典

| 字段 | 用途与缺省行为 |
| --- | --- |
| `dateBackground` | 背景图片引用；缺省为空背景 |
| `sprites` | 表情键到图片引用的映射，兼容历史混装字段 |
| `spriteConfig` | `{scale,x,y}`；UI 初始约定为 `1,0,0` |
| `customDateSprites` | 本角色新增的表情键 |
| `dateSkinSets` / `activeSkinSetId` | 多套表情图及当前套装 |
| `dateStyleConfig.style` | 电影感缺省，或其他文风 |
| `dateStyleConfig.pov` | 未设时不追加人称限制 |
| `dateStyleConfig.digDeeper` | 仅显式 `false` 关闭，默认开 |
| `dateStyleConfig.extra` | 用户额外要求 |
| `dateExtraPresets` | 本角色的额外要求模板，不是全局库 |
| `dateObserve` | 观测总开关、主题、默认字段配置、自定义字段；总开关默认关 |
| `dateAppearance` | 阅读美化；缺省 `none`，与文风无关 |
| `dateLightReading` | 原界面阅读模式的浅色开关，缺省关 |
| `dateReadingShowAvatars` | 原界面是否显示双方头像，缺省关 |
| `dateTimeAwarenessEnabled` | 线下现实时间感知，默认开 |
| `dateVoiceEnabled` / `dateVoiceLang` | 本角色见面语音开关及朗读语种；默认关/默认语种 |
| `dialogueApi` | 可选角色独立文本接口，非 Date 专属 |
| `savedDateState` | 旧播放器恢复数据，当前入口不恢复 |

以上“缺省”来自消费处对缺字段的处理，不代表所有角色创建时都会把这些字段完整写进数据库。

## 7. 上下文管线：共享记忆，不共享所有聊天工具

### 7.1 必须区分三个范围

| 范围 | 服务谁 | 当前规则 |
| --- | --- | --- |
| 当前场次 | 立绘演出、重生成、失败重试 | `dateEncounterId` 相同 |
| UI 见面历史 | 用户连续阅读和导出 | 当前角色、非群聊、`source=date`，包含旧场次和已归档原文 |
| 模型可读原文 | 本轮生成、相关记忆召回、世界书扫描 | 公共角色上下文策略，可能混有私聊/通话/见面，不等同于 UI 窗口 |

因此“阅读只加载 50 条”不代表“模型只知道 50 条”；“AI 原文被归档”也不代表“用户记录被删除”。

### 7.2 公共范围与历史转换

调用方先用 `loadCharacterContextMessages(char)` 从 DB 取得有效范围，然后由 `selectCharacterContextMessages` 复核。

- 手动模式按用户设定的原文条数取窗。
- 自适应模式按记忆整理高水位及用户断点确定范围。
- 用户断点只能进一步收窄当前有效范围。
- 空范围不能偷偷回退全库。
- 群聊不能仅因角色相同就混入单角色原文。

历史格式复用 `ChatPrompts.buildMessageHistory`，保留 role，并标注来源，例如 `[聊天] / [约会] / [通话]`。卡片转成可理解的内容，而不是把 HTML、整段卡片 JSON 或媒体引用当作普通语言。

开启独立识图时，调用方可先用 `materializeVisionDescriptions` 为可读历史补描述；未使用描述时，某些历史图片仍可能按公共多模态路径处理。不要笼统宣称所有入口永远只发纯文本。

**用户上传的场景背景和立绘并未在 DatePrompts 中自动作为视觉输入。** 换上厨房背景不等于模型因此知道地点是厨房；世界中的地点应来自正文、设定或用户明确提供的信息。

### 7.3 三条请求的真实差异

| 路径 | 可读原文 | 传统记忆 | 新鲜宫殿召回 | 最终任务 |
| --- | --- | --- | --- | --- |
| 感知开场 `buildPeekPayload` | 统一范围全部作为消息历史 | 显式 `includeDetailedMemories:false`，月度总结不因此关闭 | **没有在这条路径显式调用 `injectMemoryPalace`**；核心可能读到角色对象已有注入字段 | 第三人称开场 |
| 正常发送 `buildSessionPayload(send)` | 本轮待回复 user 从历史位置移除，再追加一次 | 使用公共默认详细记忆行为 | 调 `injectMemoryPalace`，线下时间关时传 `omitDates` | 面对面 VN 回复 |
| 普通重生成 `buildSessionPayload(reroll)` | 排除被替换 assistant，裁到触发它的 user | 同正常发送 | 同正常发送 | 保持事实与关系，尝试另一回应 |
| 开场重生成 | 排除旧开场，重新走 peek | 同感知开场 | 同感知开场 | 保留最初开场方式 |

这是最容易被泛化成“所有入口记忆完全一致”的地方。当前测试证明了原文范围与世界书的若干一致性，不等于证明每个入口都执行了新鲜向量召回。

**目标项目建议**：明确决定开场是否召回；若召回，每个请求都在局部角色快照上准备新结果，失败时清空本轮结果，别依赖上次请求在共享角色对象上留下的字段。

### 7.4 请求组装顺序

普通发送的核心顺序可以抽象为：

```text
保存或找到本轮用户消息
  -> 从 DB 读取这次的有效角色上下文
  -> 媒体可读化
  -> 排除即将被单独追加的本轮输入
  -> 本轮记忆召回 / 语义门牌准备
  -> ContextBuilder 组装人设、用户资料、记忆、日程与世界书
  -> 加面对面模式、输出协议、文风、人称、可选 OBSERVE
  -> 给实际的本轮 user 消息加一次本轮提示
  -> 末尾 system 加人物表达与用户自主权原则
  -> 请求模型
```

当前主 system 中还可能有家园定义、角色印象、自我领悟等公共核心信息。它不是“只有角色简介加最近两句”。

### 7.5 世界书的两个关键约束

使用 `ContextBuilder.buildCharacterContext` 这条公共消息管线，不能各 App 私自再解析、插入一套世界书。

1. 深度按本次真正发送的历史消息计算，不按 UI 行数、不按一段字符串里有多少换行计算。
2. 深度为 0 的条目可以位于本轮 user 之后，所以**数组最后一条不一定是用户输入**。当前实现依靠原 user 对象定位，在它身上加 VN 提醒，而不是把提醒误接到世界书。

世界书关键词扫描不应把系统玩法指令、风格范例或被隐藏的旧原文当成用户正在讨论的内容。

### 7.6 哪些聊天能力刻意没有带过来

DatePrompts 没有照搬 ChatApp 整套行为提示：

- 没有把转账、表情包、引用、日记操作、小红书等聊天工具协议都交给见面模型。
- 不额外读取实时天气/新闻、群聊背景、Notion/飞书日记标题等聊天专属背景。
- 不启用 chat/home 专用的 buff 与内心状态注入，也没有在 Date 主回复后直接运行同款情绪评估。
- 会读取公共角色核心中的已有日程；线下时间感知关闭时跳过这块今日实时安排。
- 前台现实模式可以显式加入经过隐私处理的用户位置，详见第 16 节。

“不带专门的情绪系统”不等于“角色没有情绪”：情绪依然可从人设、历史、叙述和表情标签表达；也不意味着全局其它机制绝不会间接影响召回。

## 8. 提示词设计与输出协议

### 8.1 四层规则

建议将本功能的生成规则组织成四层，而不是拼一个越来越长的万能 prompt：

1. **身份与事实**：角色、用户、关系、经历、当前场景和可知信息。
2. **互动原则**：回应真实表达，角色有自身动机，尊重用户执笔权，允许简单日常。
3. **模式约束**：这是面对面，不是 IM；开场和会话采用不同视角。
4. **表现协议**：每行标签、台词引号、可选观测、声音标签及文风。

用户自定义文风可以覆盖默认风格，不能在目标项目里被误设计成越过身份、数据授权或安全边界的权限机制。

### 8.2 当前 VN 线格式

```text
[normal] 林澈把唱片套放回桌角。
[happy] "你想听哪一面？"
[happy] 指尖停在唱机的开关边，没有替你做决定。
```

- 每个非空行是一拍，即一个 `DialogueItem`。
- 每行应有立绘表情标签；基础键为 `normal/happy/angry/sad/shy`，加本角色自定义键。
- 台词应单独一行，以引号开头；动作/旁白不要与台词混在一行。
- 表情按真实情境选择，允许连续几行相同；不要求凑齐所有表情。
- 一整轮长度随互动需要，可以很短，不强制多段升级。

**客户端真实容错**：`parseDialogue` 按换行拆分，漏表情标签会沿用之前的标签；立绘键识别使用 ASCII 字母、数字、下划线、连字符；它不是能完整理解任意散文的自然语言解析器。

比如 `他问：“你来了吗？”` 当前并不属于标准台词行；普通点播会将其视为叙述，而不是因为出现引号就读出来。

### 8.3 立绘情绪、声音情绪与声音表演是三条通道

```text
[happy] "[whispers] 我把这一面留给你了。" [v:calm]
```

- `[happy]`：视觉表情，选择哪张立绘。
- `[v:calm]`：独立语音情绪，当前接受 `happy/sad/angry/fearful/disgusted/surprised/calm`。
- 引号内 `[whispers]` 等：支持该能力的 TTS 模型的表演指令，不应被当成新立绘键。

未标语音情绪时不强行从视觉表情推导。灿烂笑脸和轻声说话可以同时成立。

### 8.4 文风、人称和可选细节提示

| 设置 | 当前选项/行为 |
| --- | --- |
| 文风 | 电影感、简洁白描、细腻文艺、轻快幽默、浓烈炽热 |
| 人称默认 | 不追加限制，随模型发挥 |
| `third-name` | 叙述中双方称名字 |
| `third-you` | 角色称名字，用户称“你” |
| `first-you` | 角色以“我”叙述，用户称“你” |
| 细节深挖 | 默认开；系统提供从已有信息寻找具体线索的方法，普通发送/重生成每轮从 8 条线索中随机取一条 |
| 自定义补充 | 原样加入，提示其文风优先级高于预设 |

人称只限制会话叙述，不改台词中正常的“我/你”；感知开场刻意保持第三人称，不套人称设置。

当前随机线索不记录抽样结果，也不保证相邻两次不同。建议目标项目按请求记录选中的 hint，便于复现；不要为了“防重复”每次加入新的人设或事实。

### 8.5 可供独立实现的 prompt 骨架

以下是本文归纳的任务骨架，不是原仓库提示词全文：

```text
角色资料：{character}
用户与关系：{user_and_relationship}
当前允许读取的经历：{context_and_memories}
当前场景：{scene_facts}

任务：在既有场景中与用户面对面互动。
先回应用户明确表达的内容；未知部分保持未知。
人物选择来自其经历与动机，写作风格不改变人物身份。
用户未写出的言语、动作、感受和决定留给用户。
允许日常、小动作、停顿与沉默，不要求每轮升级关系。

输出：每行一个表达单元，使用 {allowed_sprite_keys} 中的视觉标签。
台词和叙述分行；台词以引号包裹。
仅在启用时添加观测和相应语音标记。
采用 {style} 与 {pov}，附加用户的文风要求 {extra_style}。

本轮类型：{normal / continue / regenerate / opening}
本轮有效输入：{turn_input}
```

目标项目如已有可靠结构化输出，也可使用 JSON 事件数组代替线格式；无论如何，必须保留原文、解析诊断和降级显示，不能因一个可选面板解析失败而丢掉整轮有效文本。

## 9. 立绘播放器与阅读器

### 9.1 立绘模式

层级从后到前是：背景、立绘、文本框、输入/菜单、观测与覆盖层。

- 立绘为 2D 图片，不是这一模块内的 Live2D/VRM 控制器。
- `dialogueBatch` 保存整轮，`dialogueQueue` 保存剩余待播内容。
- 新一轮先显示第一拍；后续点击更新文字与表情。
- 当前实现打字机每约 20ms 前进一个 JS 字符位置。
- 打字过程中点击的设计意图是补全当前句；下一次才前进。
- 一轮播完再点击会重播，不新增消息，也不调文本模型。
- 用户可以通过输入按钮随时打开输入框，并非必须看完全部才回应。
- 菜单展开时点击场景先收菜单；按钮、输入框和 `.control-panel` 的点击不能推进剧情。

这些播放状态不应成为场景事实的唯一来源。画面上的当前句只是某条原文的局部。

### 9.2 连续阅读

阅读模式显示当前角色所有已加载的见面消息，包括旧场次，不限于本场。

- 用户与角色内容不同排版，原界面可开头像。
- 角色正文在渲染时解析观测、去掉控制标签，台词与叙述仍保留。
- 可长按/右键进入复制、编辑、删除、多选；启用语音时部分台词长按优先走语音收藏。
- 普通台词可逐句播放；开场消息不走这套逐句语音按钮。
- 阅读模式切回立绘不会以所浏览的某条旧消息作为新场次开场。

### 9.3 分页与滚动是功能的一部分

初次取 51 条作为探针，显示最近 50 条；更早记录用排他的 `beforeId` 游标继续取，每批 50 条。

1. 以消息 ID 合并去重，不用数组位置当身份。
2. 刷新新回复时保留用户已经展开的旧记录。
3. 切角色/场次后，通过 key、generation、refreshVersion 丢弃迟到的旧取数结果。
4. 同时多次向上触发只运行一个旧页请求；失败保留已有内容并允许重试。
5. 接近底部时新回复跟随底部；用户上翻时保留首个可见消息与它相对容器的偏移。
6. `ResizeObserver` + 下一帧校正处理内容延迟排版，不在 observer 回调里反复同步读写布局。
7. `content-visibility:auto` 让离屏正文延迟绘制，但不等于完整的 DOM 虚拟列表。

当前“靠近底部”阈值约 100px，“上翻到顶部加载”阈值约 80px。目标项目可调整，不应机械复制这些像素值。

重要移动端场景：键盘出现、输入框展开、字体加载、长正文从占位变成真实高度、删除导致内容收缩，都不应把正在读旧文的用户强拉到最新。

## 10. OBSERVE：让角色状态可看见

### 10.1 它是什么，不是什么

OBSERVE 是同一次模型回复的附加元信息：默认时间、地点、身心状态、一个细节，可按角色定制。

- 没有单独的“状态分析模型请求”。
- 没有真实生理传感器，也不是医疗状态测量。
- 生成的地点/心理是叙事信息，不能据此修改设备真实位置或当作用户已确认事实。
- 总开关默认关，开启影响下一次生成；历史不会被后台批量补出观测。

### 10.2 数据与配置分离

输出：`DateObservation {time?,place?,state?,detail?,extra?}`。

配置：`DateObserveConfig {enabled?,style?,fields?,custom?}`。

默认四维的显示标签可以修改，线格式键仍固定，以免用户把“地点”改名成“镜头”后解析器失效。每维可关闭或填写生成提示。

最多 6 个额外维度，例如“穿着”“手里的东西”。当前额外维度用稳定 ID 存值，但在线格式中按显示 label 匹配，这和默认字段不同，存在历史改名兼容问题，见第 17 节。

### 10.3 两层解析，而不是一次正则失败就全丢

**严格层始终可用**：寻找成对定界块，容忍常见括号、大小写、中文别名、英文键、全半角竖线/冒号和少量 Markdown 装饰。明确有定界符且命中一个有效字段也接受。

**宽松层只在观测开启时启用**：从开头连续扫描字段行，遇到正文即停，扫描上限约 12 行，至少命中两个不同维度才认。这样正文中的偶发“状态：……”不容易被误吞。

两层都失败时，解析器返回 `observation=null` 和完整原文。格式容错的目标是保留内容，不是悄悄猜造缺失字段。

### 10.4 呈现与设置

- 立绘模式：左上悬浮 HUD，可折叠、放大。
- 阅读模式：每条回复上方独立卡片；启用阅读美化时外层可折叠为“场景信息”。
- 5 种主题：全息、水墨、霓虹、水晶、终端。
- 设置中的预览使用固定虚构示例，不调 API。
- 一键重置清掉样式、默认字段自定义和追加字段，保留总开关。
- 原文仍保留块，之后回看可以重新解析。

**不要过度承诺当前 UI**：感知预览页直接显示 `peekStatus`，并未像会话阅读器一样统一拆出 HUD；此外 GAL 模式无新观测时可能保留上一轮面板。推荐目标项目统一解析投影，并给观测绑定来源消息 ID。

## 11. 外观、立绘与设置

### 11.1 皮肤是表情图集合，不是角色设定副本

每个 `SkinSet` 有独立 ID、名称和 `sprites` 映射。基础表情键和自定义键共用：切皮肤意味着相同 `[happy]` 显示另一张图。

- 新建空皮肤，逐个上传或填 URL。
- 激活皮肤；删除当前皮肤会回退默认立绘。
- 非空激活套装作为整套来源，当前不会把每个缺图键自动与默认套装逐键合并。
- 初始兜底：`normal -> default -> 可用表情 -> 其他非 chibi 图片 -> 头像`。
- 某拍表情没有对应图片时，当前播放逻辑通常保持上一张，而非保证每次重新兜底。
- `sprites.chibi` 属于其他玩法的 Q 版形象，必须排除，不要拿它顶半身立绘。

自定义表情需要统一校验；当前设置只做小写、空格转下划线和重复/保留名检查，而解析器限制 ASCII 标签。目标项目要让“输入端允许的键”与“模型协议能识别的键”一致。

### 11.2 图片引用与二进制分离

当前背景上传保持原画质，立绘按图片处理器默认规格压缩；字段保存 `blobref`，二进制存本地 Blob 资产库。兼容旧 data URL 与外链。

- `<TokenImg>` 用于图片字段。
- CSS 背景先通过 `useBlobRefUrl` 解析引用。
- 状态和数据库保留稳定资源引用；object URL 只是当前渲染资源，不作为持久 ID。
- 播放状态不要复制二进制。
- 目标项目应为大图、格式错误、失效链接、配额不足提供清晰反馈。

源码立绘缩放控件为 0.5–2.0；X 偏移 -100% 至 100%，Y 偏移 -50% 至 50%。这些是显示参数，不改变剧情中人与人的实际距离。

### 11.3 设置保存不是统一的“确定/取消”事务

当前行为混合了即时保存和草稿保存：

| 设置 | 当前保存时机 |
| --- | --- |
| 文风、人称、深挖开关、皮肤激活、背景/立绘 | 操作后立即更新角色 |
| 自定义补充 | 失焦保存；展开编辑器关闭时保存 |
| 补充预设 | 选择即应用，支持新建、更新和二次确认删除；删模板不清掉当前补充 |
| 观测文本字段 | 失焦保存；开关/样式等即时保存 |
| 立绘缩放与偏移 | 本地草稿，点「保存当前布置」才提交 |

所以“返回”并不等于撤销所有更改。另项目可以统一成全即时或全草稿，但应清楚标明，不要显示一个会误导用户的全局取消按钮。

长补充编辑器使用 portal 脱离祖先裁剪，跟随 `visualViewport`，处理焦点和返回；场景预览与设置内容一起滚动，可收起，不常驻挤占键盘上方空间。

### 11.4 阅读美化不改生成内容

`dateAppearance` 提供：无、纯小说、旧书纸页、静夜阅读。

- 非 `none` 默认进入阅读模式，隐藏头像/冗余标签，保留正文与可折叠补充。
- “无”停用自定义阅读 CSS，回原有界面；原界面仍可使用浅色与头像开关。
- 支持限制在 `.meeting-reading` 作用域内的自定义 CSS。
- 见面外观按角色保存，剧情外观按全局保存，不应串设置。
- 分享包仅包含样式字段，不应夹带私人聊天、提示词、API Key 或真实预览内容。

当前 CSS 校验主要检查语法和选择器作用域，是防样式外溢的软校验，不等于完整的安全沙箱。目标项目若接受第三方 CSS，还需按自己的威胁模型约束外部资源、预览隔离和能力范围。

本文不要求另项目移植官方装扮分享码/人工审核后端。用目标项目已有主题和样式系统即可，重点是“表达风格”和“阅读外观”分开。

## 12. 语音链路与成本

### 12.1 四项配置不要混在一起

1. 文本模型 API：生成这轮场景。
2. TTS 服务商 Key 与模型：生成音频。
3. 本角色音色：决定谁在说。
4. Date 语音开关与语种：是否播、播哪种语言。

当前公共路由支持 MiniMax、Fish Audio、ElevenLabs，音色字段随服务商不同。缺 Key 或音色不应阻止纯文字陪伴。

### 12.2 台词点播与 GAL 自动播放

```text
一行原文
  -> 分离视觉标签与 [v:emotion]
  -> 判断是否以台词引号开头
  -> 提取引号里的台词
  -> 按 TTS 服务商清洗/保留声音指令
  -> 非默认语种时尝试翻译
  -> 合成/读取缓存
  -> 当前音频所有者播放
```

GAL 开启语音后，对普通会话台词自动播；旁白和开场阶段不走自动台词播音。换句时应停掉上句。阅读模式逐句点播与 GAL 复用语音逻辑。

语言选项包括默认、粤语、英语、日语、韩语、法语、西班牙语、德语、俄语。当前非默认语种翻译使用全局文本 API，temperature 0.3；翻译失败回原文，并不改变已经保存的剧情正文。

这不等于“主回复直接用另一种语言生成”，也不是“语音一定有中文逐字对照字幕”。流式字幕显示实际朗读语言。

### 12.3 ElevenLabs 的当前增量能力

当前代码已接入：

- 通过带时间戳的 HTTP 流接口取得 PCM，首块到达即可播放。
- 24kHz 单声道 16-bit，成功完成后保存 WAV 与字符时间轴。
- 长文按句/段拆批，当前文本批上限约 1800 字符，不截掉后半篇。
- 字幕跟播放器音频时钟走，网络等待不伪装成已经播出的进度。
- 失败/取消不缓存残缺音频，不自动降级模型重试。
- 通过用户手势预先解锁 AudioContext，卸载时取消网络、音频队列与资源。

**范围区别**：Date 的文本回复仍先收完整内容，再进入演出。TTS 流播放不等于 Date 已实现“模型边写正文、角色边开口”的完整实时链路。

阅读里的「朗读最新一段」「连续朗读所选内容」当前仅在 ElevenLabs 分支出现，包含叙述。其取文集合实际先过滤为当前场次，因此不能宣称已支持任意跨场次多选连续朗读。

停止后再次播会从头开始；没有完整的拖动进度、暂停续读和有声书书签。

### 12.4 缓存有两层，不能只看底层

- 公共持久缓存按实际 TTS 参数计算键，可包含文本、模型、音色、语种和声学参数。
- DateSession 自己的内存缓存主要按台词文本索引，没有覆盖所有这些参数。

所以“底层缓存参数完整”不保证“换语种/换音色后页面绝不会播旧声音”。目标项目应让所有缓存层使用统一的有效请求键，并给翻译结果单独建缓存。

当前普通 TTS 缓存倾向长期保留，无自动淘汰保证；持续使用会占存储。另项目建议提供用量查看与明确的缓存清理入口，不把清缓存等同于删除原文或用户收藏。

### 12.5 语音收藏

台词支持长按/右键打开收藏操作。收藏记录包含来源类型、角色、来源键、原始台词、实际朗读文本/语言、源消息时间和音频资源。

- 已有声音可以直接保存。
- 没有缓存时，点收藏可能先合成，意味着额外调用。
- 取消收藏只应处理收藏及其资源，不删除见面原文。
- 当前某些来源键含消息 ID 和行号；编辑消息后行号重排可能改变对应关系。

目标项目若需稳定收藏，建议使用持久 `beatId` 或同时保存原文版本/内容摘要，而非只靠“第几行”。

### 12.6 请求预算表

| 操作 | 文本生成 | 其他可能调用 |
| --- | --- | --- |
| 打开列表/直接见面/切显示模式 | 0 | 通常无 |
| 每次感知/重新感知 | 1 次主回复 | 已开启的前台位置、历史识图等准备 |
| 每次发送/继续/重生成 | 1 次主回复 | 可选记忆召回、识图、位置 |
| 点一次未缓存的异语台词 | 可能 1 次翻译 | TTS 合成 |
| 连续朗读长文 | 可能 1 次翻译 | 多批 TTS；不是必然只有一次 HTTP 请求 |
| 回复后记忆整理 | 不是每轮必调 | 达阈值时提取、向量、组织；共享计数可能触发消化 |
| 编辑文本/换皮肤/看记录 | 0 | 外链图片可能产生普通资源网络请求 |

不能用固定“每次陪伴只消耗一次 API”的说明覆盖所有可选能力，也不能把取消请求解释为上游已停止计费。

## 13. 请求、重试与修订

### 13.1 API 选择与响应

文本回复用 `resolveDialogueApi`：公共规则是 App 显式覆盖优先，其次角色独立配置，再到全局。Date 当前调用没有单独传 App 覆盖，因此实际是角色优先于全局。

- URL/Key/Model 整套选择，不拼接不同配置的字段。
- 普通发送与开场 temperature 用选定配置，缺省 0.85。
- 重生成 temperature 至少为 0.9，不低于用户配置基线。
- Date 当前固定 `max_tokens:8000`，并未消费私聊可配置的 `maxTokens`。
- `stream` 可跟随配置，但 `safeResponseJson` 收完整 body 再解析，UI 不逐 token 渲染文本。
- 解析兼容 JSON/SSE、HTML 错误页、空回复；非成功 HTTP 状态抛错。
- Anthropic 原生兼容依赖公共网络出口 `fetchLlm` 的转换，不是 Date 组件自己实现 Messages 协议。

目标项目应该复用自己的模型适配器，不为这个功能另写一套密钥选择与兼容接口。

### 13.2 正常发送

1. 生成前记录本次角色和场次 ID。
2. 如果最后一条 date 消息是同场次、相同内容的 user，视作未完成输入的重试，不再插入重复 user。
3. 否则先保存 user；`continue` 带专用 metadata。
4. 重读有效上下文，构建请求。
5. 请求成功后保存 assistant，带原场次 ID。
6. 若当前仍是这个场次才刷新当前 UI。
7. 异步触发记忆尾段。

请求期间输入和继续按钮不可再次正常发送。输入失败时临时保存 `pendingRetryText`，即使父级列表尚未刷新，重试按钮仍可取到原输入。

错误文本仅用于当前画面提示，不应作为成功的 assistant 原文保存。

### 13.3 重生成

只能重生成当前场次的最新 assistant，不对任意历史楼层重掷。

- 开场：用保存的 `dateOpeningMode` 重建对应开场任务；保留 `isOpening` 和场次标记。
- 普通回复：排除旧 assistant，找到触发这轮的用户输入；把跨 App 共享历史裁到这个用户消息，防止更晚的聊天被误当成此次输入。
- API 失败时旧回复仍在。
- 成功才删旧并保存新回复；因此 ID 与 timestamp 当前会变化。
- 普通回复重生成也会触发记忆尾段；开场分支没有同样调用。

这里保护了“模型请求失败不丢原答”，但还没做到“替换存储失败不丢原答”或“并发修改时不覆盖新内容”。目标项目应采用第 18 节的版本化原子替换。

### 13.4 编辑、删除与记忆的边界

阅读模式与独立记录页都能改/删原文，操作完成会标记云端上下文快照待刷新。

- 文本编辑不是重新生成，不花主回复额度。
- 删一条不会自动删邻近回合。
- 批量删除当前逐条调用删除方法，不是整批单事务保证。
- 改删原文不会自动撤销已经提取的长期记忆、重写月度总结或删除独立语音收藏。
- 当前播放批次在最新 assistant 内容改变时会尝试重解析，但 HUD 等派生状态并未全部统一随版本失效。

目标项目需要在确认框/帮助里说明“删除原文”和“撤销派生记忆”是两种操作，不能给用户虚假的彻底遗忘承诺。

## 14. 记忆衔接：最小功能也要把接口留对

### 14.1 为什么回聊天还能接上

见面写入同一角色的公共 `messages`，不是只留在 DateSession 的 React state 中。

- 私聊 UI 会过滤 `source=date`，不把整段小说画成聊天气泡。
- 模型历史加载不能照抄这个 UI 过滤，仍按公共范围得到可读的见面原文。
- 历史携带来源标签，区分“手机里发过的话”和“面对面做过的事”。
- 回聊天时，ChatPrompts 的模式切换提示把输出格式重新锚回 IM；可以承接经历，不继续输出 VN 标签和大段旁白。

这套“共享事实、隔离表现”的机制，比让每个 App 单独维护一份剧情摘要更重要。

### 14.2 当前回复后做什么

`runMemoryPalacePostHook` 在普通回复和普通重生成后异步执行：

1. 从最新角色列表重新确认宫殿仍开启。
2. 检查 Embedding 和轻量 LLM 配置；轻量 LLM 未配置地址时存在回退全局主 API 的路径。
3. 调 `processNewMessagesWithAutoArchive` 做统一水位缓冲检查与整理。
4. 有新节点时提供整理结果 UI。
5. 和聊天共享按角色的消化轮数，达到条件时调用认知消化。

调用处虽然给出最近 50 条作为材料提示，也不能把它解释成整个归档系统只处理这 50 条；公共记忆管线有自己的读取与水位规则。

**不应宣称的行为**：每发一条就立即生成一条长期记忆；点离开必然写总结；感知成功就一定触发整理；页面关闭后一定跑完。

### 14.3 如何接已有记忆模块

目标项目最少提供这三类能力即可：

```text
loadAllowedCharacterHistory(characterId, boundary)
prepareMemoryContext(characterId, visibleHistory, currentTurn)
notifyCommittedCharacterTurn(characterId, committedMessageIds)
```

它们可以映射到项目已有服务，不要求函数名相同，也不要求使用向量库。

- 已有统一历史：给消息增加来源与场次，不另造一份平行人生。
- 历史分 App 存储：先实现有明确排序和权限边界的聚合读取，避免一上来大规模搬库。
- 没有长期记忆：先做到可靠原文保存与跨界面读取，再分阶段接归档。
- 有长期记忆：给提取器保留完整可读原文、来源与消息 ID，失败不能推进归档水位。

详细的宫殿、事件盒、门牌和消化设计在上一份记忆手册中；它们不是体验 MVP 的全部前置条件。

## 15. 历史、导出与跨入口配合

### 15.1 按次与按日期

当前独立记录页读取当前角色的全部 date 消息，不受宫殿高水位限制。

**按次优先级**：

1. 有 `dateEncounterId`：按 ID 归组，跨日和迟到回复仍归原场。
2. 无场次 ID、有旧 `isOpening`：从开场到下一开场归为一次，不用 30 分钟之类阈值乱切。
3. 更老的无锚点记录：按设备自然日期兼容归组，不冒称恢复出了真实场次。

**按日期**：按用户设备本地日分组，可汇总同一天多场。组间新旧排序可切，组内始终正序。

有年月筛选、日期定位、组折叠展开。按次筛选命中组内某日时保留整个场次，而不是只截掉其中一天的半场。

### 15.2 TXT 导出

- 导出本次、当天或当前角色全部见面。
- “全部”会重新读库，不应只导出当前 UI 已加载的 50 条。
- 文本包含角色、整理方式、导出时间、每条真实收发时间和说话人。
- 原文协议与舞台内容保留，当前不是“只导出纯台词”。
- 文件名清理系统不允许的字符，UTF-8 BOM 兼容常见文本阅读器。
- Web 下载/分享和 Android 原生分享走公共导出工具。

TXT 是可读记录，不是完整可恢复备份；它不含所有 metadata、二进制立绘、声音和角色设置。另项目要另设结构化备份契约。

### 15.3 备份、角色卡与外观分享分开

- 私人完整备份承载角色设置、消息和资产关联。
- 角色卡分享不是私人系统搬家。当前敏感字段过滤明确剥离独立 API、见面背景、声音偏好、补充预设和旧恢复快照等。
- 不要据此推断角色卡里所有其它 date 字段都被过滤；具体应以显式导出 schema 为准。
- 阅读美化分享只传样式白名单，与聊天原文完全不同。
- 目标项目建议默认最小白名单，而非“整个角色对象展开后删几个 Key”。

### 15.4 本地主动消息的配合

当前 `OSContext` 的本地旧调度路径有两层照顾：

- DateApp 活跃且目标角色相同时，已排好的本地定时消息先延后投递，不删除；本地主动生成则跳过本轮。
- 最近真实消息来自 date，且距离不到 3 小时时，本地主动消息提示可使用“刚分开”的语境，而非误说很久没联系。

判定使用 App/角色级状态，不是严格“正在 session”状态。因此不能说它精确识别了正在陪伴的每个阶段；也不能从这些本地判断推导云端主动消息 2.0 已有同样的实时暂停保证。

Date 的消息增删改调用 `markAmsgStateDirty`，让后续云端快照从 DB 重新读取素材；这不表示本次 Date 主回复在 Worker 上生成。

另项目建议使用显式、可失效的会话 presence 信息，而不是“当前打开的 App 名称”等于“物理相处已成立”。

### 15.5 可选 SAR 临时表达层

已有其它玩法给角色或用户装载临时模块时，Date 会复用一个额外表达协议；没有对应状态时不注入这个协议，不应为普通陪伴增加容器与负担。

- 一次模型输出可以同时产生正常含义 `CHAR_TRUE` 和临时外显 `CHAR_SURFACE`，必要时还有用户输入的外显版本。
- 数据库 `content` 保存正常/规范语义，临时外显放在 `metadata.sarModuleSurface`；不是两份互不相关的新经历。
- 阅读和立绘提供外显/真意切换；单句播音使用当前呈现的文本，连续全文朗读存在第 17 节列出的差异。
- 临时说话方式不能被记忆提取器固化为永久人格、真实意愿、关系升级或新事实。
- 模块结束后恢复正常表达，不是持续叠加一个文风预设。

可迁移的是“事实层与表现层分开”的思想。另项目没有临时表达玩法时完全可以不实现 SAR，不必移植其商店、资源或世界观。

## 16. 时间、现实信息与隐私

### 16.1 三种时间不能混用

| 时间 | 例子 | 处理 |
| --- | --- | --- |
| 绝对事件时间 | 消息保存、请求超时、经过多久 | 真实时间戳相减 |
| 角色墙上时间 | 提示词“现在几点”、角色作息 | 角色时区，未设置则设备时区 |
| 用户界面时间 | 历史日期分组、消息时间、导出日期 | 设备本地时间 |

OBSERVE 的场景时间是叙述值，可以比“系统当前分钟”更自然，不能反过来覆盖数据库 timestamp。

### 16.2 线下时间开关

`dateTimeAwarenessEnabled !== false` 时，Date 自己的场景时间与历史时间戳按现实时间参与上下文。开场还会提供大致互动间隔：不足 5 分钟通常不提示，之后按分钟/小时/天表达；部分夜间判断按角色时区。

关闭后：

- 不按现实已过几小时/几天强行跳剧情时间。
- 不附加历史现实时间戳。
- 不注入今日实时日程和前台用户定位。
- 去掉系统附加的传统记忆、宫殿召回日期标注。
- 沿用最近记录的剧情时间、地点与事件。

但这**不清除原文中已写的日期，不改 DB，不隔离共享记忆，也不自动变成“虚构剧场”模式**。若用户不希望架空经历进入正常角色记忆，应使用独立虚构命名空间，而不是只关时间。

聊天时间开关与 Date 专用开关是两个设置；公共核心某些时间项仍有自身门禁。目标项目应对四种开关组合写测试，不凭字段名认定所有时间块都已完全解耦。

当前感知页面顶部的 `virtualTime` 实为设备时钟显示，和模型使用的角色时区不是同一概念。这是需要产品明确的差异，不应通过手工增减小时修补。

### 16.3 真实位置属于可选前台能力

当前 Date 通过 `includeUserLocation` 复用公共定位服务。是否真正取定位，还受本机开关、角色授权和隐私保护控制。

- 默认关闭；未获角色授权时不发起定位。
- 每次先检查隐私圈；命中或精度边界不确定时不查询地图。
- 圈内仅输出“家附近”等用户别名，不传中心坐标、半径或原始地址。
- 圈外按用户所选服务直连；不借 Worker/代理转发坐标，不失败后暗换供应商。
- 原始坐标、隐私圈、地图 Key 不进模型提示词、普通日志、备份或云端状态。
- 模型仍可能看到经过过滤的位置文本，中转站也可能看到它；local-first 不等于生成过程零数据外发。
- 定位只作参考，不强迫改变剧情地点；关闭定位也不会撤回之前已发给模型或写入正文的地点文字。

另项目不需要定位就不要实现这一项。陪伴核心体验不依赖真实 GPS。

## 18. 给另一个项目的推荐实现架构

### 18.1 先适配现有项目，而不是移植整个 OSContext

建议逻辑边界如下，技术栈和文件名可按目标项目调整：

```text
MeetingEntryView        角色入口、三种开场、来源路由
MeetingSessionView      场景、阅读器、输入与操作
MeetingController       语义回合、场次、请求生命周期
MeetingRepository       原文、场次、回合状态、修订事务
CharacterContextPort    现有角色/记忆/世界书的授权读取
MeetingPromptBuilder    场景规则与输出协议
MeetingParser           原文 -> 观测 + 台词/旁白 + 诊断
MeetingPlayer           当前拍、立绘、动画与阅读书签
MeetingVoiceController  音频所有权、翻译、缓存、字幕
MeetingSettings        文风、外观、资产与可选能力
```

已有统一消息服务就复用，不要求真的新建每个类。关键是职责能单测，不让一个组件同时管理数据库事务、模型协议、世界书、声音和所有 UI 状态。

### 18.2 建议的数据补强

以下是**目标模型建议，不是 SullyOS 当前已实现字段**：

```ts
type MeetingEncounter = {
  id: string;
  characterId: string;
  origin: 'chat' | 'meeting' | 'shortcut';
  opening: 'approach' | 'invite' | 'direct';
  createdAt: number;
  endedAt?: number;
};

type MeetingTurn = {
  id: string;                     // 逻辑回合，重试不变
  encounterId: string;
  kind: 'input' | 'continue' | 'opening';
  displayInput?: string;
  userMessageId?: string;
  replyMessageId?: string;
  status: 'pending' | 'generating' | 'generated' | 'committed' | 'failed' | 'cancelled';
  revision: number;
};

type ParsedMeetingReply = {
  sourceMessageId: string;
  sourceRevision: number;
  parserVersion: number;
  observation: null | Record<string, string>;
  beats: Array<{
    id: string;
    kind: 'dialogue' | 'narration';
    text: string;
    spriteKey?: string;
    voiceEmotion?: string;
    speechText?: string;
  }>;
  diagnostics: string[];
};
```

补强目的：

- 原文和请求状态分开，避免把“还没保存”当“需要再生成”。
- 观察、声音、收藏和播放器都绑定同一消息版本。
- 场次边界与来源即使没有开场也明确。
- 解析器升级可重建显示，不改原文。
- `origin` 只控制导航，不应被拿来推断用户已做出剧情动作。

### 18.3 推荐请求协议

```text
1. 建/读逻辑 turn，先持久化用户原文或 continue 语义。
2. 获取 per-encounter 同步锁，为这次尝试分配 requestId。
3. 冻结角色、输入、源消息 revision 与设置版本。
4. 读取授权上下文；显式准备本轮记忆，不修改共享角色对象。
5. 构造一次有效请求，记录非敏感诊断信息。
6. 请求支持 abort 和截止时间，但不自动把未知结果重发成第二笔费用。
7. 校验正文；把成功返回视为 generated，和数据库 committed 区分。
8. 事务提交新消息/修订 + turn 完成状态；校验源版本未变。
9. 只有提交成功才更新主时间线并投递记忆处理事件。
10. UI 仅消费仍属本场次/本代次的结果；后台结果保留正确归属。
```

若需要多标签页或跨设备执行，内存锁不够，应有存储层唯一约束/版本检查。持久中间结果也有隐私与配额成本，按目标项目能力选择，不必强上分布式系统。

### 18.4 推荐重生成协议

1. 固定目标消息 ID、revision 和对应 turn。
2. 旧答保留可见；构建截止到原用户输入的上下文。
3. 用同一个语义转换器处理普通输入与 continue。
4. 生成成功后，对旧答做 compare-and-swap 事务替换；失败不删旧答。
5. 保留原逻辑顺序，另记 `editedAt/generatedAt`，不靠新时间戳把它排成刚发生的另一件事。
6. 使该版本的观测、播放队列、音频选择、派生索引失效。
7. 若保留多个候选，明确只有选中版本进入未来上下文和记忆处理。

### 18.5 推荐解析策略

- 正文为空或只有推理：生成失败，不伪造场景。
- 正文有效、可选 OBSERVE 格式坏：保留正文，给可选块诊断，不吞整轮。
- 缺表情/缺图片：使用稳定视觉兜底，不阻塞阅读。
- 混合动作与台词：可以降级为叙述，或明确提示修复；不要默认把所有内容送声音。
- 不用全局正则删除所有 `[...]`，而是只处理已识别的协议节点。
- 渲染用户与模型文字使用安全文本/项目既有安全渲染器，不把模型输出当可执行 HTML。

## 19. 分阶段实施计划

### 阶段 0：目标项目勘察

Agent 先说明现有角色表、聊天消息 schema、模型适配器、上下文边界、记忆尾段、导航、资源库和测试框架分别在哪里。

输出字段映射与改动文件计划，明确复用什么、缺什么。不要未读项目就照搬本仓库目录、装一批重复依赖。

### 阶段 1：可靠的文字陪伴 MVP

必须有：

- 从角色/聊天进入，三种开场，未接受的预览不入经历。
- 明确场次 ID 与语义回合，及时保存用户和角色原文。
- 面对面上下文与用户自主权原则。
- 输入与继续，等待、失败、重试、离开。
- 连续阅读、按场次回看，至少可导出可读文本。
- 原子重生成，编辑/删除的基本语义。
- 与原聊天共享可读经历，回聊天恢复格式。

本阶段可以没有立绘、TTS、定位和向量库。先确保“确实在相处”和“不丢数据”，不是先做一个只有背景的空壳。

### 阶段 2：表现层

- 统一 parser，立绘表情与逐拍演出。
- 阅读/立绘无重复生成切换。
- 角色级背景、皮肤、文风、人称与补充模板。
- OBSERVE 两层解析、来源绑定、可折叠显示。
- 分页、滚动锚点、小屏键盘与返回层级。

### 阶段 3：声音与记忆增强

- 优先接目标项目已有的一种 TTS，别一开始同时接三家。
- 参数完整的缓存、停止/切换/退出取消、播放错误。
- 可选翻译、长文阅读、字幕、声音收藏。
- 接已有长期记忆处理；建立消息版本与派生记录关系。
- 用实际设备验收权限、音频解锁、后台挂起和存储配额。

### 阶段 4：可选生态

再考虑自定义 CSS 分享、真实位置、跨设备恢复、独立剧情模式、临时表达模块、与后台主动消息的协作。

这些不应阻挡基础陪伴上线，也不应为了“功能参考完整”强制使用原项目服务。
