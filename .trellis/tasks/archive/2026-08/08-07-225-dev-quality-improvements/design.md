# 2.2.5-dev 稳定性与可用性修复：技术设计

## 1. 边界与目标

父任务只负责三项子任务的共享契约、执行顺序、版本文档和最终集成审查：

- 群聊多角色回复可靠性；
- 角色音色 Sheet 滚动；
- 普通聊天与 RP 的单条消息删除。

性能专项已解除父子关系，不属于本轮实现或验收范围。

## 2. 共享数据流

```text
用户操作
  → Chat / RP / Settings Compose 回调
  → 对应 ViewModel 与局部 UiState
  → Support / Coordinator / Repository
  → Store / Room / AiGateway
  → Flow 回流到消息列表、RP 映射列表、Sheet 或提示条
```

Screen 不直接接触 DAO、Entity、Retrofit 或原始 SSE；共享删除规则只有一个底层所有者。

## 3. 跨子任务契约

### 3.1 群聊

- 保留现有串行回合顺序和单角色最多两次尝试。
- “模型正文完成持久化”是生成提交边界；后处理失败不得覆盖已完成正文。
- 所有普通异常、取消和会话切换都必须恢复稳定的发送/Loading 状态。
- 日志只记录角色 id、turn、attempt、stage 和安全错误类别。

### 3.2 音色 Sheet

- 只调整 `AssistantVoiceProfileSheet` 的单一滚动容器、滚动状态和系统安全区。
- 保存仍通过现有 `onSaveProfile`；草稿、试听、文件处理和设置模型保持不变。

### 3.3 消息删除

- 普通聊天和 RP 共享 `ConversationRepository.deleteMessage` 与原子 Store 契约。
- 同一 Room 事务移除目标、清理顶层/parts 引用、来源记忆、摘要和摘要分段。
- RP 删除使用底层 `sourceMessageId`；撤回继续走现有独立流程。
- 删除不调用附件文件清理，不修改 Entity、schema 或数据库版本。

## 4. 依赖与执行顺序

```text
群聊可靠性 ───────┐
                  ├→ 单条删除 → 三项集成回归 → 版本收口
音色滚动 ─────────┘
```

- 群聊与音色修改范围独立，可以并行实现和检查。
- 单条删除会触及 RP ViewModel、回调和测试；为避免与群聊任务写冲突，在群聊完成后
  再接入 RP 删除链路。
- 删除底层纯变换/Room 设计保持独立，但最终统一由单条删除子任务交付。

## 5. 兼容性、迁移与回滚

- 预期不需要 Room schema 版本变化；若实现发现必须改表，立即返回规划阶段。
- 群聊后处理隔离与总流程状态兜底分开验证和回滚。
- 音色布局调整不触及 ViewModel 或持久化，可独立回滚。
- 删除入口可暂时隐藏回滚，但已成功物理删除的数据不可恢复，因此必须先通过原子事务
  和二次确认测试。
- 工作区已有用户改动，任何提交和回滚都只能针对本任务文件。

## 6. 集成验收

- 三个子任务分别满足自己的 AC 和质量门禁。
- 普通聊天与 RP 删除共用同一底层语义，UI 不出现两套不一致规则。
- 群聊和删除共同触及的 RP 状态、回调和测试在集成后重新运行。
- 版本文档统一记录 2.2.5-dev；未获得最终 APK 前不更新下载元数据。
